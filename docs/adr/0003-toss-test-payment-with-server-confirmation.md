# 토스페이먼츠 테스트 결제와 서버 확정으로 후원을 받는다

## 배경

4단계는 방송자 후원을 추가한다. 실제 돈은 오가지 않지만 결제 서비스의 테스트·샌드박스 모드로 결제 요청과 승인 확인 흐름을 갖춰야 한다. 화면의 성공 표시만으로 후원을 확정하면 안 되고, 같은 승인 통지가 반복돼도 한 번만 적립해야 한다.

검토한 방법:

1. **토스페이먼츠 결제창(API 개별 연동 키) + 서버 승인**
2. **포트원(PortOne)**: 여러 PG를 묶는 중계 계층이 하나 더 생긴다.
3. **직접 만든 가짜 결제사**: 외부 서비스가 없어 "결제 서비스의 테스트 모드" 요구에 맞지 않는다.

## 결정

1번을 택한다.

- 서버가 결제 전에 후원 주문(`대기`)을 만들고 수신자(방송 소유자)와 금액을 고정한다. 브라우저는 그 `orderId`·금액으로 토스 JS SDK v2 결제창을 연다.
- 승인 통지는 두 경로로 받는다. 성공 리다이렉트(`GET /donations/success`)는 토스 승인 API를 호출하고, 웹훅(`POST /donations/webhook`, 비로그인·CSRF 제외)은 본문을 믿지 않고 토스 조회 API로 상태를 다시 확인한다. 둘 다 같은 확정 로직을 쓴다.
- 확정 전에 리다이렉트 금액 = 주문 금액, 토스 응답 상태 `DONE`·금액·`orderId` 일치, 방송이 남아 있고 소유자가 수신자와 같음을 확인한다. 어긋나면 주문을 `실패`로 두고, 이미 승인된 결제는 토스 취소 API로 되돌린다.
- 중복 방지: `대기 → 확정` 전이는 한 번만 일어나도록(조건부 갱신) 하고, `orderId`·`paymentKey`에 유니크 제약을 둔다. 이미 확정된 건의 승인 통지는 같은 결과를 돌려주고 아무것도 바꾸지 않는다.
- 토스 호출은 `PaymentGateway` 인터페이스 뒤에 두고 자동 테스트는 가짜 구현을 쓴다. 키(`TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`)가 없으면 앱은 뜨고 후원만 막는다(요청 503, 화면 안내).

## 결과

- 좋은 점
  - 금액과 수신자를 서버가 정하고 결제사에 직접 확인하므로, 화면이나 리다이렉트 쿼리를 조작해도 후원이 확정되거나 부풀지 않는다.
  - 새로고침·웹훅 재전송 같은 반복 통지가 DB 제약과 상태 전이로 막혀 합계가 한 번만 늘어난다.
  - 결제사 경계가 인터페이스라서 테스트가 네트워크 없이 성공·실패·불일치·중복을 재현한다.
- 나쁜 점
  - 웹훅은 결제사가 앱에 닿아야 하므로 로컬에서는 공개 주소(예: cloudflared)와 개발자센터 웹훅 등록이 필요하다. 없으면 성공 리다이렉트 경로만 쓰인다.
  - 결제를 끝내지 않은 `대기` 주문은 정리하지 않고 남는다(내역·합계에는 들어가지 않는다).
  - 토스 결제창이 페이지를 떠나므로 라이브 시청 중 후원하면 결과 화면을 거쳐 시청 화면으로 돌아와야 한다.
- 선택하지 않은 이유
  - 포트원: 이 과제에 필요한 것은 카드 결제 하나라 중계 계층의 이점이 없다.
  - 가짜 결제사: 실제 결제 서비스의 승인 API·웹훅을 다루는 경험과 요구를 충족하지 못한다.
