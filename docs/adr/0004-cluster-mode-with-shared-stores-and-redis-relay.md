# 클러스터 모드: 공용 저장소와 Redis 시그널링 중계로 인스턴스를 바꿔 끼울 수 있게 한다

## 배경

5단계는 서버를 로컬 클러스터에서 여러 인스턴스로 띄우고, 부하에 따라 인스턴스 수가 자동으로 늘고 줄게 하라고 한다. 인스턴스가 바뀌어도 로그인 세션·업로드한 영상·라이브 상태·댓글·후원이 유지돼야 한다. 4단계까지의 서버는 인스턴스 하나를 전제로 했다.

- DB가 H2 파일이라 여러 인스턴스가 함께 열 수 없다.
- 로그인 세션이 인스턴스 메모리에 있다.
- 라이브 시그널링 방(방송자·시청자 WebSocket)이 인스턴스 메모리에 있어, 방송자와 시청자가 다른 인스턴스에 붙으면 연결되지 않는다.
- 서버가 시작될 때 라이브를 모두 종료하고(`LiveStartupCleanup`), 방송자 접속 유예 검사를 메모리의 방으로 한다. 스케일 아웃으로 인스턴스가 하나 뜨면 진행 중인 방송이 모두 끝나고, 다른 인스턴스에 붙은 방송자를 "접속 안 함"으로 오판한다.

검토한 방법:

1. **오케스트레이터**: kind + Kubernetes HPA / Docker Desktop Kubernetes / Docker Compose + 직접 만든 스케일러.
2. **공용 저장소**: Postgres + Redis(세션) + 공유 볼륨(영상) / Postgres만(세션 JDBC) / 영상을 MinIO에.
3. **라이브**: Redis로 방 상태 공유와 메시지 중계 / 프록시가 라이브 ID로 같은 인스턴스에 고정.
4. **기존 실행**: 프로필 없이 실행하면 지금 그대로 / 언제나 Postgres + Redis.

## 결정

- **kind + HPA**: 클러스터 설정(`k8s/`)과 kind 설정을 저장소에 둔다. 앱 Deployment, CPU 사용률 50% 기준 HPA(최소 2, 최대 5, 축소 안정화 60초), metrics-server, NodePort Service(요청 분산), Postgres와 Redis(각 1개)로 구성한다.
- **공용 저장소**: 회원·방송·댓글·후원은 Postgres, 로그인 세션은 Spring Session Redis, 업로드 영상은 모든 앱 파드가 같은 경로로 마운트하는 공유 볼륨에 둔다. 영상 저장 코드는 바꾸지 않는다.
- **Redis 시그널링 중계**: 방송자 접속 기록과 시청자 명단(정원 검사 포함)을 Redis에 두고, 각 인스턴스는 자기 앞으로 온 메시지를 Redis pub/sub으로 받는다. 방송 종료 알림도 모든 인스턴스에 퍼뜨린다.
- **인스턴스가 사라져도 방송은 이어진다**: 영상은 P2P라 시그널링 연결이 끊겨도 흐른다. 방송자 화면은 시그널링이 끊기면 다시 접속하고, 서버는 방송자 접속 기록이 접속 유예 시간 넘게 없을 때만 방송을 종료한다. 클러스터 모드에서는 시작 시 전체 종료를 하지 않는다.
- **단독 모드 유지**: `cluster` 프로필이 없으면 지금처럼 H2 파일·메모리 세션·메모리 방으로 혼자 동작한다. 1~4단계 실행·확인 절차는 그대로 유효하다.
- **부하**: k6 스크립트를 클러스터 안 Job(grafana/k6 이미지)으로 돌린다.
- **검증**: Testcontainers로 Postgres·Redis를 띄워, 서버 두 개를 동시에 올려 세션 공유와 인스턴스 간 시그널링을 테스트한다. Docker가 없으면 이 테스트만 건너뛴다.

## 결과

- 좋은 점
  - 어떤 인스턴스가 요청을 받아도 같은 로그인·방송·댓글·후원을 보고, 스케일 인으로 파드가 사라져도 진행 중인 라이브가 끝나지 않는다.
  - 단독 실행은 외부 서비스 없이 그대로라 앞 단계 확인 절차와 테스트가 바뀌지 않는다.
- 나쁜 점
  - 라이브 방 로직이 단독(메모리)과 클러스터(Redis) 두 구현을 갖는다. 같은 인터페이스 뒤에 두고, 공통 동작은 같은 테스트로 확인한다.
  - 공유 볼륨은 kind 단일 노드의 볼륨이라 노드가 여러 개인 실제 클러스터에서는 ReadWriteMany 스토리지나 오브젝트 스토리지가 필요하다.
  - Postgres·Redis는 한 개씩이라 그 자체는 이중화하지 않는다(로컬 확인 범위).
  - 여러 인스턴스가 동시에 시작하며 `ddl-auto=update`로 스키마를 맞추므로, 처음 배포할 때는 경합을 피하려고 DB 준비 뒤에 앱을 띄운다.
- 선택하지 않은 이유
  - Compose + 직접 만든 스케일러: 스케일러를 직접 만들고 검증해야 하고, HPA가 같은 일을 표준으로 한다.
  - 세션 JDBC: 라이브 중계에 어차피 Redis가 필요하다.
  - MinIO: 업로드·구간 재생 코드를 크게 바꿔야 하는데, 로컬 단일 노드에서는 공유 볼륨으로 충분하다.
  - 라이브 ID 고정 라우팅: 그 인스턴스가 스케일 인으로 사라지면 방송이 끊긴다.
