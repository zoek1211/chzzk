# 송출 키를 없애고 로그인 세션의 소유자 검사로 라이브를 보호한다

## 배경

2단계에는 회원이 없어서 라이브를 시작하면 서버가 송출 키(비밀 값)를 만들어 그 화면에만 알려 주었다. 방송자는 WebSocket 접속 뒤 첫 메시지 `{type:"auth", key}`로, 종료 요청은 `X-Broadcast-Key` 헤더로 그 키를 보냈고, 서버에는 키의 해시만 저장했다. 이 방식은 키를 가진 화면만 방송을 다룰 수 있어서, 화면을 새로고침하거나 다른 기기로 옮기면 방송을 종료할 수 없었다. 3단계에서는 회원과 소유자가 생겨 "누가 이 방송의 주인인가"를 로그인한 회원으로 직접 판단할 수 있다.

검토한 방법:

1. **송출 키 유지**: 로그인한 회원이 시작하되 키도 그대로 쓴다.
2. **세션의 소유자 검사**: 키를 없애고, 라이브에 소유자(회원)를 기록한 뒤 모든 방송자 동작을 로그인 세션의 회원이 소유자인지로 검사한다.

## 결정

2번을 택한다. 송출 키 발급·해시 저장·`X-Broadcast-Key`·`{type:"auth"}` 메시지를 모두 없앤다.

- 라이브 시작은 로그인한 회원만(비로그인 401), 시작한 회원이 소유자다. 회원당 방송 중인 라이브는 하나(초과 시 409).
- 종료·삭제는 소유자만(비로그인 401, 다른 회원과 소유자 없는 기존 라이브 403). 삭제는 종료된 라이브만(방송 중이면 409).
- 방송자 WebSocket(`/ws/live/{id}/broadcaster`)은 핸드셰이크 때 HTTP 세션의 Spring Security 컨텍스트에서 회원을 읽어, 그 회원이 방송 중인 라이브의 소유자일 때만 받아들인다(`HandshakeInterceptor`). 비로그인 401, 다른 회원·종료된 라이브 403, 없는 라이브 404. 방송자 접속을 받아들였다는 확인으로 서버가 `{type:"authenticated"}`를 한 번 보낸다. 시청자 연결은 지금처럼 누구나 된다.
- 접속 유예, 연결 끊김 자동 종료, 시청 정원, 재시작 시 종료 처리는 그대로 둔다.

## 결과

- 좋은 점
  - 소유자는 어느 기기에서든 로그인만 하면 자기 방송을 종료할 수 있고(다른 기기에서 종료하면 방송자 화면도 종료 알림을 받는다), 분실한 휴대폰의 방송도 끊을 수 있다.
  - 별도 비밀 값(키 생성·해시·전달)이 없어 코드가 줄고, 인증 수단이 로그인 하나로 통일된다. 권한은 화면이 아니라 서버가 매 요청과 매 접속에서 검사한다.
- 나쁜 점
  - 방송자 WebSocket이 세션 쿠키에 의존한다. 로그인 세션이 만료되면 새 방송자 접속은 거절된다(이미 맺은 연결은 유지된다). WebSocket 경로는 CSRF 대상에서 빠져 있으므로, 접속 허용은 세션 소유자 검사에만 기댄다.
  - 회원 기능 이전에 만든 라이브는 소유자가 없어 아무도 종료·삭제할 수 없다. 방송 중이던 것은 재시작 때 종료로 바뀌고, 그 뒤로는 보기만 된다.
  - 기존 데이터 파일의 `broadcast_key_hash` 열은 `ddl-auto=update`가 지우지 않는다. 이 열이 NOT NULL로 남은 옛 파일에서는 새 라이브를 저장하지 못하므로, 개발 데이터는 비우고 다시 시작해야 한다.
- 선택하지 않은 이유
  - 송출 키 유지: 소유자 개념과 같은 일을 하는 두 번째 인증 수단이 생기고, 키를 잃으면 소유자도 방송을 못 다루며, 화면 메모리에 비밀 값을 들고 있어야 한다.
