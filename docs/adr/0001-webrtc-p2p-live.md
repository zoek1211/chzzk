# 라이브 방송은 WebRTC P2P + WebSocket 시그널링으로 전달한다

## 배경

휴대폰 카메라·마이크로 송출하는 라이브 방송을 로그인 없이 다른 화면에서 실시간으로 볼 수 있어야 한다. 서버는 Spring Boot 단일 애플리케이션이고, 별도 미디어 서버를 운영하기 어렵다. 종료된 라이브는 다시 보지 않으므로 영상을 서버에 저장할 필요가 없다. 시청 정원은 방송마다 작은 수(기본 5명)다.

검토한 방법:

1. **WebRTC P2P + WebSocket 시그널링**: 방송자 브라우저가 시청자마다 연결을 맺고 영상을 직접 보낸다. 서버는 offer/answer/candidate만 전달한다.
2. **MediaRecorder + MSE 서버 중계**: 방송자가 조각 영상을 WebSocket으로 서버에 올리고, 서버가 시청자에게 뿌려 `MediaSource`로 재생한다.
3. **외부 미디어 서버(WHIP 송출 + HLS 시청 등)**: SRS, MediaMTX 같은 서버가 영상을 받아 변환·배포한다.

## 결정

1번을 택한다. 서버는 `/ws/live/{id}/broadcaster?key=…`, `/ws/live/{id}/viewer` WebSocket으로 시그널링 메시지만 중계하고, 영상은 방송자와 시청자 브라우저가 WebRTC로 직접 주고받는다. 서로 다른 네트워크에서 직접 연결이 안 될 때를 위해 STUN은 기본 제공하고 TURN은 환경변수로 선택 설정한다. 휴대폰 카메라 접근(`getUserMedia`)에 HTTPS가 필요하므로 cloudflared 터널 또는 직접 HTTPS를 쓴다.

## 결과

- 좋은 점
  - 서버가 영상을 받거나 저장하지 않아 대역폭·CPU 부담과 별도 인프라가 없다. 의존성은 Spring WebSocket뿐이다.
  - 지연이 짧다(1초 안팎). 브라우저 표준 API만 쓰므로 iOS Safari, Android Chrome에서 추가 설치 없이 동작한다.
  - 방송자 연결이 끊기면 곧 방송 종료로 처리하기 쉽다.
- 나쁜 점
  - 방송자가 시청자 수만큼 영상을 따로 인코딩·전송하므로 휴대폰 부하가 시청자 수에 비례한다. 그래서 시청 정원을 두고 화질(1280x720, 30fps 이하)을 제한한다.
  - 엄격한 NAT·방화벽이나 서로 다른 네트워크에서는 TURN이 없으면 연결이 안 될 수 있다. TURN은 직접 운영하거나 외부 서비스를 써야 한다.
  - 서버에 영상이 없으므로 녹화·다시보기, 대규모 시청자(수백 명 이상) 확장은 이 구조로 할 수 없다. 필요해지면 외부 미디어 서버(SFU 또는 WHIP/HLS)로 바꿔야 한다.
- 선택하지 않은 이유
  - MediaRecorder + MSE 중계: 서버가 영상 조각을 받아 시청자 수만큼 다시 보내야 해 서버 대역폭이 늘고, 조각 단위 버퍼링으로 지연이 커지며, iOS Safari의 `MediaSource` 지원이 제한적이다.
  - 외부 미디어 서버: 확장성과 호환성은 좋지만 서버 한 대 추가 운영, 설정, 배포 부담이 이번 범위(작은 정원, 로그인 없음)에 비해 과하다. HLS는 지연도 수 초 이상이다.
