# 과제 단계 진행

치지직 과제는 단계별 과제다. 단계 N은 Codemit 문제 페이지 하나에 대응하고, 앞 단계 기능을 유지한 채 이 저장소 위에 쌓는다. 채점은 **정적 평가**: 채점자는 소스·설정·README만 읽고 앱을 실행하지 않는다. 그래서 README가 기능만큼 중요하다.

| 단계 | 문제 페이지 | 태그 |
| --- | --- | --- |
| 1 | `https://classroom.codemit.kr/classes/6/problems/61/submit` | `step-1` |
| 2 | `https://classroom.codemit.kr/classes/6/problems/62/submit` | `step-2` |
| 3 | `https://classroom.codemit.kr/classes/6/problems/63/submit` | `step-3` |
| N | 앞 단계 번호 + 1 (페이지 제목으로 확인) | `step-N` |

## 단계

1. **요구사항 읽기.** 브라우저로 문제 페이지를 열어 목표·구현 범위·직접 확인·제출 안내와 **체크리스트** 항목을 모두 읽는다. 로그인 페이지가 나오면 사용자에게 브라우저 패널에서 로그인해 달라고 한다. 완료: 체크리스트 항목마다 그것을 충족할 코드나 README 위치를 말할 수 있다.
2. **설계 합의.** `grill-with-docs`로 설계 트리를 끝까지 묻는다. 정해진 용어는 그 자리에서 `GLOSSARY.md`에 반영하고, 되돌리기 어려운 선택은 `docs/adr/`에 ADR로 남긴다. 완료: 열린 질문이 없고, 사용자가 합의 요약을 확인했다.
3. **스펙과 티켓.** `to-spec`으로 스펙 이슈를 만들고, `to-tickets`로 수직 슬라이스 티켓을 나눠 사용자 승인 후 스펙의 하위 이슈로 올린다. 마지막 티켓은 README·ADR 마무리다. 완료: 모든 티켓에 수용 기준과 선행 관계가 있다.
4. **구현.** `main`에 `step-(N-1)` 태그가 있는지 확인하고, 통합 브랜치 `wip/step-N`을 만든 뒤 `implement-spec`으로 구현한다. 구현 에이전트는 Sonnet 모델로 각자 워크트리에서 띄우고, 프롬프트는 [implementer-brief.md](implementer-brief.md)를 가리키며 티켓별 사항만 적는다. 구현 브랜치가 통합 브랜치 최신 커밋을 이미 포함하면 오케스트레이터가 직접 앞으로 감기(`git merge --ff-only`)로 합치고, 충돌이 나는 병합만 머지 에이전트에게 맡긴다. 완료: 모든 티켓이 `wip/step-N`에 합쳐졌고 전체 테스트가 통과한다.
5. **리뷰와 실제 확인.** `code-review`(표준·스펙 두 축)를 돌린다. 표준 리뷰어에게는 [CODING_STANDARDS.md](../../CODING_STANDARDS.md)를 기준으로 준다. 지적을 한 에이전트에 모아 고친다. 그다음 앱을 띄워 브라우저로 새 화면과 이전 단계 화면을 직접 눌러 본다. 완료: 리뷰 지적이 반영됐거나 제외 이유가 있고, 브라우저 콘솔 오류가 없다.
6. **README 점검.** `python3 scripts/check_readme_stages.py`를 돌리고, 아래 README 규칙을 하나씩 대조한다. 완료: 스크립트가 통과하고, 이번 단계 체크리스트의 README 관련 항목마다 해당 섹션이 있다.
7. **병합·태그·제출.** 사용자 확인을 받고 `wip/step-N`을 `main`에 합친 뒤 `step-N` 태그를 달고 push해 CI가 통과하는지 본다. 사용자 확인을 다시 받고 문제 페이지에 GitHub 저장소 주소(`https://github.com/zoek1211/chzzk`)로 제출한 뒤 채점 결과를 기다려 보고한다. 완료: 체크리스트 판정을 사용자에게 전달했다. 통과 후 티켓은 코멘트를 남기고 닫고, 에이전트 워크트리와 `ticket-*` 브랜치를 정리한다.

## README 규칙

- README는 **누적 문서**다. 단계마다 "구현 범위"와 "직접 확인 절차"에 `### N단계` 소단원을 추가하고, 앞 단계 소단원(구현 범위 표, 확인 절차, curl 예시, 테스트 목록)은 원문 그대로 둔다. `scripts/check_readme_stages.py`가 각 `step-*` 태그 시점의 소단원과 비교한다.
- 새 단계가 앞 단계의 동작을 바꿨으면(예: 3단계의 송출 키 폐지), 앞 단계 원문은 그대로 두고 그 소단원 맨 위에 `> N단계에서 바뀐 점: …` 한 줄과 새 단계 소단원 링크를 붙인다. 검사 스크립트는 이 형식의 줄만 예외로 본다.
- 매 단계 공통 필수: 실행 방법, 환경변수 표와 예시(`.env.example`과 일치), 이번 단계 구현 범위, 직접 확인 절차. 체크리스트에 따로 적힌 README 항목(예: 2단계의 휴대폰 연결·권한 설정, 3단계의 공개 범위)은 같은 단어로 소제목을 단다.
- 제목과 맨 위 단계 표에 새 단계와 태그를 추가한다.
- 비밀 값은 예시 자리표시자로만 쓴다.

## 함정

- **테스트 데이터 디렉터리.** 테스트 프로세스의 기본 데이터 경로는 `build/test-data`이고, 테스트가 저장소의 `./data`를 새로 만들면 `./gradlew test`가 실패한다. `SpringApplicationBuilder`로 띄울 때는 `--chzzk.data-dir=...` 커맨드라인 인자로 넘긴다(`properties()`는 `application.properties`에 밀린다).
- **`hidden` 속성.** `display`를 지정한 클래스가 `hidden`을 덮는다. 공통 CSS의 `[hidden] { display: none !important; }`를 유지한다.
- **브라우저 패널의 카메라.** 패널은 카메라·마이크를 막는다. 장치가 필요한 흐름은 WebSocket·HTTP 수준으로 확인하고, 실기기 확인은 README 절차로 사용자에게 남긴다.
- **`bootRun`과 정적 파일.** 실행 중인 서버는 시작 시점의 리소스를 쓴다. CSS·템플릿을 고쳤으면 서버를 다시 띄워 확인한다.
- **Gradle 실행.** Bash에서 Gradle이 훅에 막히면 context-mode 실행 도구로 돌리고 실패·요약만 출력한다.
